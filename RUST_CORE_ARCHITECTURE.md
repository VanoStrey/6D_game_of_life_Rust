# Rust Core Architecture: 6D Game of Life

Настоящий документ описывает архитектуру, внутреннее устройство, математическую модель и результаты верификации ядра (simulation core) проекта **6D Game of Life** на языке Rust.

Ядро разработано с приоритетом **100% математической и поведенческой эквивалентности оригинальной Java-реализации** при достижении максимальной производительности, эффективной локальности данных в кэше CPU и полного отсутствия динамических аллокаций памяти в горячем цикле симуляции.

---

## 1. Архитектура проекта

Ядро изолировано от графического бэкенда (`wgpu`, `winit`, `egui`, окно, ввод) и скомпоновано в виде независимой библиотеки `six_d_game_of_life`:

```text
src/
├── lib.rs                     # Публичный фасад библиотеки
├── main.rs                    # Автономный CLI-раннер и бенчмарк-инструмент
├── simulation/
│   ├── mod.rs
│   ├── coords.rs              # Многомерные координаты, шаги (strides), 6D <-> 1D маппинг
│   ├── grid.rs                # Линейное непрерывное хранилище (ByteGrid)
│   ├── rules.rs               # Правила перехода поколений (динамические проценты)
│   └── simulation.rs          # Двойная буферизация, последовательный и Rayon-шаг
└── projection/
    ├── mod.rs
    └── projection.rs          # Точная 3D проекция гиперкуба по осям X, Y, Z
```

## 2. Структура хранения Grid

Вместо шестиуровневого дерева указателей Java (`boolean[][][][][][]`) используется линейный одномерный массив:

```rust
pub struct Grid {
    pub dims: GridDimensions,
    pub data: Vec<u8>,
}
```

### Преимущества:
1. **Предсказуемый memory layout**: Все ячейки расположены непрерывно в оперативной памяти.
2. **Превосходная cache locality**: Для сетки $6^6 = 46\,656$ ячеек весь массив занимает всего **45.5 КБ**, что полностью помещается в L2-кэш процессора.
3. **Отсутствие битовых масок в горячем цикле**: Использование `u8` (0 = dead, 1 = alive) обеспечивает прямое чтение ячейки за одну инструкцию `mov` без накладных расходов на bit-twiddling, что ускоряет многократное чтение окрестности.
4. **Легкая заменяемость**: Интерфейс `Grid` абстрагирует прямой доступ, позволяя при необходимости адаптировать хранилище под `bitvec` или разреженные структуры.

## 3. Индексирование и порядок координат

Отображение многомерного пространства в 1D строго повторяет структуру массивов Java:
- В Java массив объявлен как: `gameBoard[a][b][c][d][e][f]`, где `a` меняется медленнее всего, а `f` — быстрее всего.
- Индекс `f` соответствует измерению 0 (активно при $D \ge 1$, размер `size`).
- Индекс `e` соответствует измерению 1 (активно при $D \ge 2$, размер `size`, иначе 1).
- Индекс `d` соответствует измерению 2 (активно при $D \ge 3$, размер `size`, иначе 1).
- Индекс `c` соответствует измерению 3 (активно при $D \ge 4$, размер `size`, иначе 1).
- Индекс `b` соответствует измерению 4 (активно при $D \ge 5$, размер `size`, иначе 1).
- Индекс `a` соответствует измерению 5 (активно при $D = 6$, размер `size`, иначе 1).

Формула линейного индекса:
$$\text{linear\_index} = f \cdot 1 + e \cdot S_0 + d \cdot (S_0 S_1) + c \cdot (S_0 S_1 S_2) + b \cdot (S_0 S_1 S_2 S_3) + a \cdot (S_0 S_1 S_2 S_3 S_4)$$

Обратное преобразование в `coords_from_index`:
$$f = (\text{idx} / \text{stride}[0]) \pmod{S_0}$$
$$e = (\text{idx} / \text{stride}[1]) \pmod{S_1}$$
$$d = (\text{idx} / \text{stride}[2]) \pmod{S_2}$$
$$c = (\text{idx} / \text{stride}[3]) \pmod{S_3}$$
$$b = (\text{idx} / \text{stride}[4]) \pmod{S_4}$$
$$a = (\text{idx} / \text{stride}[5]) \pmod{S_5}$$

## 4. Алгоритм обхода соседей и устранение аллокаций

В Java метод `formatCounters` создавал `new int[6]` на каждой итерации проверки каждого соседа, порождая до **34 миллионов аллокаций** за шаг.

В Rust обход окрестности развернут без динамических аллокаций:
- Координаты соседей `na, nb, nc, nd, ne, nf` и проверка выхода за границы выполняются непосредственно на регистрах CPU:
  ```rust
  let na = if dn[5] == 3 { a as isize - 1 + a1 as isize } else { 0 };
  ...
  if na >= 0 && (na as usize) < sn[5] && ... {
      let n_idx = dims.linear_index(na as usize, ...);
      if current.get_raw(n_idx) != 0 { count_live += 1; } else { count_die += 1; }
  }
  ```
- **Аллокаций в горячем цикле**: **0 байт**.

## 5. Правила перехода (Transition Rules)

Математика расчета порогов воспроизводит формулы Java с точностью до бита:
```rust
let count_all = count_live + count_die;
let min_neighbors = (count_all as f64 / (100.0 / self.percent_min_neighbors)) as i32;
let max_neighbors = (count_all as f64 / (100.0 / self.percent_max_neighbors)) as i32;
!(count_live > max_neighbors || count_live < min_neighbors)
```
- Деление `100.0 / percent` эквивалентно умножению на процент.
- Приведение к `i32` выполняет усечение к нулю (truncation towards zero).
- Пороги вычисляются относительно `count_all` (число реально попавших в границы ячеек), поэтому на гранях и ребрах допустимый диапазон сжимается.

## 6. Двойная буферизация и параллелизация (Rayon)

Симуляция использует два независимых буфера одинакового размера:
```rust
pub struct Simulation {
    pub current: Grid,
    pub next: Grid,
    pub rules: Rules,
    pub generation: u64,
}
```

1. **Double Buffering**: Чтение выполняется исключительно из `current` (read-only), запись следующего поколения — в независимый слайс `next`. В конце шага указатели меняются местами: `std::mem::swap(&mut self.current, &mut self.next)`. Перевыделение памяти отсутствует.
2. **Параллелизм**: Для сеток $\ge 512$ клеток `step()` автоматически использует `step_par()` с `par_chunks_mut()` библиотеки `rayon`. Потоки обрабатывают крупные непрерывные блоки ячеек без локов и разделяемых мутабельных состояний.

## 7. 3D Проекция

Отображение многомерных ячеек на 3D-сцену строго соответствует Java-коду:
$$\mathbf{X} = d + c \cdot (\text{size} + \Delta)$$
$$\mathbf{Y} = e + b \cdot (\text{size} + \Delta)$$
$$\mathbf{Z} = f + a \cdot (\text{size} + \Delta)$$

Габариты визуального 3D-пространства:
- $D = 1$: $1 \times 1 \times \text{size}$
- $D = 2$: $1 \times \text{size} \times \text{size}$
- $D = 3$: $\text{size} \times \text{size} \times \text{size}$
- $D = 4$: $[(\text{size} + \Delta) \cdot \text{size}] \times \text{size} \times \text{size}$
- $D = 5$: $[(\text{size} + \Delta) \cdot \text{size}] \times [(\text{size} + \Delta) \cdot \text{size}] \times \text{size}$
- $D = 6$: $[(\text{size} + \Delta) \cdot \text{size}] \times [(\text{size} + \Delta) \cdot \text{size}] \times [(\text{size} + \Delta) \cdot \text{size}]$

## 8. Known Java Bugs Preserved Intentionally

Для обеспечения безусловной совместимости с оригинальным поведением Java в текущей версии сохранены следующие особенности:

1. **Дефект проверки окрестности (`sum == 0`)**:
   - Условие `a1 + b1 + c1 + d1 + e1 + f1 == 0` исключает углового соседа $(-1, -1, -1, -1, -1, -1)$.
   - Центральная точка $(0, 0, 0, 0, 0, 0)$ соответствует индексам цикла $(1, 1, 1, 1, 1, 1)$ с ненулевой суммой и **ошибочно включается в число проверяемых соседей**.
   - Живая клетка увеличивает собственный счетчик `count_live` на 1, а мертвая — счетчик `count_die` на 1.
2. **Граничная асимметрия решетки**:
   - В углу с нулевыми координатами $(0,\dots,0)$ смещение $(-1,\dots,-1)$ находится за пределами сетки и отсекается проверкой границ (проверяется ровно $2^D$ точек).
   - В углу с максимальными координатами $(\text{size}-1,\dots,\text{size}-1)$ смещение $(-1,\dots,-1)$ валидно, но отбрасывается условием `sum == 0` (проверяется $2^D - 1$ точек).
3. **Осцилляция при $\text{size} = 1$**:
   - При размере ребра 1 единственная клетка имеет `count_all = 1`.
   - Пороги вычисляются как $[0, 0]$.
   - Мертвая клетка имеет 0 живых соседей $\in [0, 0]$ и рождается; живая клетка имеет 1 соседа $\notin [0, 0]$ и умирает. Клетка вечно осциллирует между 0 и 1 с периодом 2.

## 9. Результаты тестирования и верификации

Тестовый набор включает 13 автоматических тестов:
1. `test_exact_equivalence_against_java_oracle` — пошаговое сравнение 20 детерминированных тестовых сценариев, экспортированных непосредственно из оригинального Java-класса `LogicGameOfLive` (все размерности 1D..6D, размеры 1, 2, 3, 4, 6, по 3 последовательных поколения в каждом). Сравнение показало **100% совпадение всех состояний** как в последовательном, так и в параллельном режиме.
2. `test_java_neighbor_bug_center_cell_counted_as_neighbor` — верификация учета клетки самой в себе.
3. `test_java_neighbor_bug_minus_one_corner_is_dropped` — верификация потери соседа $(-1,\dots,-1)$.
4. `test_boundary_corner_asymmetry` — верификация асимметрии углов на границах.
5. `test_size_1_oscillation_across_all_dimensions` — верификация осцилляции при $\text{size}=1$ для размерностей от 1D до 6D.
6. Модульные тесты проекции и координатных преобразований.

## 10. Результаты бенчмарков (Criterion Baseline)

Замеры проводились на архитектуре Apple Silicon (release-профиль, LTO, opt-level=3):

| Конфигурация | Число клеток | Число проверок соседей | Время шага (Rust) | Throughput (клеток/сек) | Аллокации памяти |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **1D, size=100** | 100 | 200 | **1.25 µs** | 80.0 Mcells/s | 0 B |
| **3D, size=10** | 1 000 | 26 000 | **47.6 µs** | 21.0 Mcells/s | 0 B |
| **4D, size=6** (дефолт UI) | 1 296 | 103 680 | **118.9 µs** | 10.9 Mcells/s | 0 B |
| **6D, size=6** (Rayon par) | **46 656** | **33 965 568** | **14.8 ms** | **3.15 Mcells/s** | **0 B** |

### Сравнение с Java:
- В Java один шаг симуляции 6D ($\text{size}=6$) занимал **секунды** и генерировал более **1.35 ГБ** временных объектов `int[6]` в куче с неизбежными Stop-The-World паузами GC.
- В Rust симуляция 6D выполняется за **~14.8 мс** (~67 поколений в секунду) с **нулевыми аллокациями**, что позволяет плавно рендерить 6D-симуляцию в реальном времени при 60 FPS.
